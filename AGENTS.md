# KnightLauncherPlus — Agent Instructions & Architecture Guide

## Overview
KnightLauncherPlus is an independent hard fork of `lucasluqui/KnightLauncher`. It does not send changes upstream on its own; genuine upstream bugs found here are reported to the maintainer of this fork, who decides per issue whether to raise a PR. It is a dedicated fork with extended features including custom server joining, built-in game server hosting, and enhanced modding capabilities.

## Upstream Synchronization Policy
- Upstream remote: `https://github.com/lucasluqui/KnightLauncher.git`
- Upstream commits are periodically merged into `main` via `git merge upstream/main --no-ff`.
- When resolving merge conflicts, preserve KnightLauncherPlus features (custom servers, built-in server hosting, dark theme, rebranded URLs) while adopting upstream engine modernizations (Java 25 target, HiDPI scaling, modernized threading, ordered properties).

## Build & Runtime Environment
- **Java**: Java 25 LTS (64-bit HotSpot VM).
- **Build Tool**: Apache Maven (`pom.xml`) via repository wrapper (`mvnw` / `mvnw.cmd`).
  - Copy `deploy.properties.template` to `deploy.properties` first (once); the build bakes it into the jar. CI and the deploy scripts do this for you.
  - Standard development build: `./mvnw clean package` (env `dev`: local Flamingo)
  - Production build: `./mvnw -Denv=prod clean package` (what CI releases)
  - Automated tests: `./mvnw test`. The server tests (`SpiralServerTest`, `SpiralServerProcessTest`) skip themselves without game data. To run them, make a folder with symlinks to the game's `code` and `rsrc`, a copy of `getdown.txt`, and the two scene files in `KnightLauncher/server/scenes/` (or in the folder's `scenes/`, which the server copies from), then `./mvnw -DargLine="-Dsk.gameDir=<folder>" test`. They cover startup against real data, the auth timeout, the session cap, garbage input and the stdout/stdin protocol.
  - 1-click build & deploy to local game dir: `scripts\build_and_deploy.bat` (or `./scripts/build_and_deploy.sh`). It defaults to the `prod` env, `-Dev` / `--dev` for `dev`; `-Run` / `--run` launches afterwards.
- **Game Classpath Dependencies**:
  - `lib/projectx-pcode.jar`: Required for compiling against Three Rings Clyde, Presents, Tudey, and Spiral Knights data classes. Copied from `<game>/code/projectx-pcode.jar`.
  - `lib/discord-rpc-20220830184500.jar`
  - `lib/image4j-0.7.2.jar`

## Package & Component Architecture
- `com.lucasluqui.bootstrap`: Native launcher entry point and runtime loader (`Bootstrap.java`, `Main.java`).
- `com.lucasluqui.launcher`: Core application lifecycle (`LauncherApp`, `LauncherGlobals`, `CustomColors`, `Fonts`, `Stylesheet`, `Updater`).
- `com.lucasluqui.launcher.server`: **Built-in Spiral Knights Game Server Emulator & UI** (flat package).
  - **Process model**: the emulator needs the game's jars (`code/projectx-pcode.jar`, which is never bundled) and runs in its own JVM. `ServerHostManager` (launcher side) starts `SpiralServer.main` with the launcher's console Java, a classpath of `code/projectx-pcode.jar` first (it carries patched copies of libraries such as Guava) then `KnightLauncher.jar`, cwd = game dir. Not `config.jar`: private launches patch it and Windows would keep it locked. It parses stdout lines `[READY] port=N`, `[FATAL] msg`, `[PLAYERS] n` (`ServerNet`), forwards everything else to the console panel and sends console commands over stdin. The process stops on `stop` or when stdin closes.
  - Keep launcher infrastructure (`LauncherGlobals`, `Log`, samskivert `Logger`) out of the server classes: on the game classpath they clash with the game's obfuscated samskivert copy.
  - `ServerNet`: constants, protocol prefixes, `validPort`, LAN address lookup (no game classes, safe to load in the launcher). `ServerHostManager`: lifecycle and registration of the **Local Server** entry (not selected automatically). `SpiralServer`: listener (loopback unless started with `--lan`), 32-session cap, 10 s auth timeout, console commands. `ClientSession`: Presents/Narya protocol, scene and combat plumbing; services with their own logic are `ServiceHandler`s registered in its `InvocationRouter` by service code (`KnightHandler`, `MailHandler`), `LoginHandler` does the key exchange and sign-in, and handlers only see the session through `SessionContext` (add new services the same way, not as more `ClientSession` methods); player objects are created only after `AuthRequest`; client OIDs start at 10000, party OIDs at 1000000 (500/501 are the scenes). `SceneManager`, `SceneCollision`, `CombatWorld`, `VanillaCombatController`, `SceneNetworkManager`, `DObjectManager`, `ItemCatalog`, `InstalledConfigManager`, `MovementConfig` (`KnightLauncher/server/server.properties` or `server.properties`).
  - Scenes `1` (Haven) and `294` (Training Hall) are never bundled and not in a stock install: the client downloads them from the official servers when you visit them and caches them in `<game>/scenes/<id>`. `SceneManager.importClientScenes` copies them from there into `KnightLauncher/server/scenes/<id>` at server start (existing copies are kept); the server reads that folder first, then `rsrc/scenes/<id>` and `scenes/<id>`. `rsrc/config/*.dat` come from the game install. Missing scenes fail the start with a message saying to visit Haven and the Training Hall once. Verified on a real Steam install: it starts with an empty `scenes/`, and after visiting Haven and the Training Hall the client's cache holds files named exactly `1` and `294`, which the server loads.
  - Client services: the game client looks services up by class (`Client.getService`) while it builds its windows and throws in every frame if one is missing (UplinkService did: loading stuck at 82%). `ClientSession.CLIENT_SERVICES` lists the extra marshallers offered in the bootstrap data (found by scanning the client's `getService` calls); every request to them gets the generic confirm reply. When a new `X isn't available` shows in `projectx.log`, add its marshaller there. `ClientServicesTest` checks each one loads.
  - Everything the server prints is also written to `KnightLauncher/server/server.log` (previous run: `server.log.old`) by `ServerHostManager`; read that and the game's `projectx.log` when debugging a client.
  - Database (`server/db`): one SQLite file, `KnightLauncher/server/world.db` (`org.xerial:sqlite-jdbc`; the launcher jar keeps only the Mac, Windows and Linux x64/ARM natives via `src/assembly/jar-with-dependencies.xml`). `Database` is a single connection used through `write`/`read` (transactions, WAL, foreign keys, `PRAGMA user_version` + `MIGRATIONS`: never edit a released migration, append one). `AccountStore` signs in or creates an account (PBKDF2-HMAC-SHA256, 600k iterations, per-name lockout after 5 wrong passwords); `KnightStore` keeps knight names unique server-wide, ignoring case, independent of account names. Tests use `Database.inMemory()` and a fast hasher. `MailStore` keeps mail per knight (200 per mailbox, 30-day expiry except NON_EXPIRING, ids start at 1 because the client reserves 0).
  - Login (`LoginHandler`, `ServerKeys`, `SessionTokens`): the game does a key exchange (`SecureRequest` -> `SecureResponse`), then sends an `AESAuthRequest` encrypted with the secret. The server owns an RSA key (`KnightLauncher/server/keys/server-private.key`, owner-only); the launcher writes its public half (`ServerKeys.publicKeyProperty()`) into the Local Server's `key.public`, so only games set up by the launcher can sign in (others get `m.failed_to_secure`; unencrypted logins are refused). The password arrives as the MD5 hex of what was typed; the server stores a PBKDF2 hash of that. The first login of a new username creates the account; wrong password `m.invalid_password`, lockout `m.too_many_attempts`, bad session id `m.session_expired`, Steam-ticket usernames (`steam:<id>`) `m.steam_error` (the game's `steamClient` flag is true for typed logins too, so it is not used). After login the game keeps the returned session id instead of the password and reconnects with it (`SessionTokens`, 12 h, memory only).
  - Knights (`KnightHandler`): knight service methods 4 choose, 5 create, 6 delete, 7 check a name; the game's own name rules and message keys are in `KnightStore.nameError` (letters, spaces, dashes; at least 4 letters; `m.name_in_use`). Names are unique server-wide and independent of the account name. A first login creates one knight named after the account when that is valid. Each knight owns its items (`knight_items`: weapons and gear, unique ids that are what the game sees, `equip_slot`/`quick_slot` for where they are worn) and crowns (`knight_state`); `KnightInventory` puts them on the player object when a knight is chosen and saves them when gear moves, a knight is switched and the session ends. A knight's first play grants the starter kit (`ItemCatalog.starterKit`: a worn set plus every weapon, level 10). Items: `GearCatalog` lists everything the game can create by kind; a cleared dungeon level gives each knight a piece of gear that fits the depth. There is no shop (the game's shop windows are opened by NPCs in town that this server does not emulate), crafting, forging, trading or mail attachments.
  - Mail (`UplinkMailService`, service code 40): get (6), mark read (11), delete (4), send (5), email data (12); mail with attachments is refused (`m.access_denied`); the "new mail" entries on the player object are kept in step and pushed to an online recipient. Stub `com.samskivert.depot.util.ByteEnum` exists because the game's enum writer checks it and only the reading side ships with the game.
  - Chat (`ChatHandler`): scene speech (service 20, method 1, no reply listener) and party speech (31) are `MessageEvent`s named `crowd.chat` carrying a `UserMessage` on the scene/party object to everyone in the place, the speaker included; whispers (chat service 4, method 3) go to the recipient's own object and are answered `(idle ms, away message)` (the game casts both) or `m.user_not_online`; away (4/1) sets `awayMessage`; the console `say`/`broadcast` reach every player (mode 4). Muting, slash commands and the rate limit are the game's own. Calls without a reply listener reach handlers with `listener == null`.
  - Friends (`SocialHandler`, `FriendStore`, service 42): a friend request is mail of type FRIEND (the requesting knight in `mail.attach_knight_id`, shown to the game as a `FriendRequest` attachment); accepting is claiming that mail (Uplink 40/1 or 40/2), which makes the friendship (mutual, two rows, 250 max) and sends both sides an `EntryAddedEvent` on `friends`; 42/6 unfriends. Presence (`Whereabouts.Online/Offline`, `knights.last_seen`) is pushed as `EntryUpdatedEvent` on login, knight switch, scene change and logout. Reply to a request before pushing events to the same client (the test client drops events that arrive before the reply). Social calls 3 to 5 are confirmed and ignored.
  - Items: the game's "Equip as..." menu is item service method 3 `(id, slot)`; method 9 moves/unequips. Per-knight crowns and worn gear persist (see Knights); the item list is still one fixed starter list.
  - Parties (`Party`, `PartyManager`, `PartyHandler`, service 30; `server.maxPartySize`, default 8, max 8): every player is always in a party (alone at first); a shared `PartyObject` per party holds members/health/status, and changes are applied to it and sent as events to the members. Invite (30/2) adds a `Notification$PartyInvite` (key `PARTY_INV:<partyOid>`) to the invitee; the game answers through social 42/5 `(key, 1|0)` (the accept value is inferred from bytecode). The party's longest-standing member is its leader (boot 30/1, dungeon start). Party chat (31) reaches all members. The game's party display was made for 4; 8 is untested there.
  - Dungeons (`DungeonLayout` pure geometry, `DungeonSceneBuilder` map, `Dungeon` level logic, `DungeonManager`, `CombatWorld` monsters): the game ships no dungeon layouts or enemy AI, so levels are generated (chain of rooms and corridors, floor/wall tiles, globals and player start copied from the Training Hall) and registered as extra scenes (`SceneManager.registerCombatScene`, ids 900000+ recycled, versions always newer so the game never shows a cached old level; dropped when empty). Commands: the game's `/` commands live entirely in the client (`ProjectXChatDirector`; an unknown command is refused locally, nothing reaches the server, and `/help` text comes from the client's message bundles, so neither can be extended from here). Several of its developer commands call the game's admin service instead, and `AdminHandler` (service 55, `ProjectXAdminMarshaller`, last in `CLIENT_SERVICES`) answers three: `/mission [depth] [easy|medium|hard]` (method 3) starts a dungeon for the party (leader, in town), `/depth <n>` (39) sets the party's start depth and the next level's depth, `/debug <command>` (20, answered with text) runs `dungeon`, `companions [n]`, `leave` and `help`. Every other admin call is refused with `m.access_denied` (no administrator exists). Leaving the party in a dungeon also returns the knight to town. Reply to an admin call before starting anything: starting sends events, and the test client drops events that arrive before the reply. Monsters come from the game's own spawn tables (`Dungeon.FAMILIES`) and depth/health scaling, appear per room, wake when a knight enters the room, chase, and swing their real attacks (only `DamageRegion` damage is carried out; status effects, projectiles and summons are not). Difficulty scales with party size (`Dungeon.monstersInRoom/healthFactor/damageFactor`). A knocked-out knight stands up at the entrance after 3 s. Kills pay crowns (6 x depth); when every monster is dead, walking to the end of the last room sends the party one level deeper. Companions (`Companion`): the party leader sets `/debug companions <n>` (n plus the party fits `server.maxPartySize`); they join the next dungeon as real knights in the scene (occupants, the same `Dungeoneer` actor and `VanillaCombatController` driven by synthetic input frames: walk to the nearest monster in 10 units, swing every 0.7 s, otherwise follow the nearest player), with finite health (100, hit by monsters like players, gone for the level when it runs out) and gear drawn at random from items the game can create (`creatable`, helm/armor/shield, swords only for weapons because the server's combat cannot carry out every gun/bomb attack yet) whose rarity fits the depth (`Companion.fitsDepth`). They count toward party size for monster numbers and health. Monsters' damage is cut to 40% (`Dungeon.ARMOR_FACTOR`) until armor is modeled. Console `dungeon clear` kills every monster (testing). Not verified with a real client: that the game renders generated maps, the monsters' look while moving/attacking (no animations are driven), and the party HUD in a dungeon.
  - Tests: `TestClient` is a real game client over a socket (same streams and crypto); `LoginProtocolTest`, `KnightProtocolTest` and `MailProtocolTest` drive the server through it. Accounts persist in the game folder's database, so tests use names of their own.
  - Settings: `ServerSettings` is the single list of every setting (key, type, default, range, group); `MovementConfig` (what the server reads), `ServerPropertiesFile` (reads/writes the optional `KnightLauncher/server/server.properties`, or `server.properties` in the game folder; only non-default values are written, unknown keys are kept) and the launcher's **Server Settings** window (`ui/ServerSettingsDialog`, opened from the Server Hosting screen) all use it, so a new setting is added in one place: add a `Def` there, then the `ss.<key>` and `ss.<key>.desc` strings to every `lang_*.properties` (`ServerSettingsLocaleTest` checks English). Keys (defaults): `movement.deltaIntervalMs` (20, the Haven update interval; the client sends input every 33 ms), `movement.trainingDeltaIntervalMs` (20) and `movement.actorStateIntervalMs` (20), both multiples of the first, `combat.burstIntervalMs` (100), `server.maxSessions` (32), `server.authTimeoutSeconds` (10), `movement.baseSpeed`, `movement.speedMultiplier`, `movement.bounds.*`, `movement.logEveryPackets`. Port and LAN access are the launcher's own settings (`server.port`, `server.allowLan`) shown in the same window. Changes apply the next time the server starts. The server prints `[NETWORK][TICK] rateHz=... maxGapMs=...` every 100 ticks; `rateHz` should be near 50 and `maxGapMs` close to the interval.
  - `ui/`: Server Hosting tab (`ServerHostUI`, `ServerConsolePanel`, `ui/handler/ServerEventHandler`). Settings keys: `server.port`, `server.allowLan`.
- `src/main/java8/.../runtime/Updater.java` hardcodes the self-update repository; `UpdaterRepoTest` keeps it equal to `LauncherGlobals`.
- `com.lucasluqui.launcher.flamingo`: Server list and metadata client (`FlamingoManager`). Supports official and manually added custom servers.
- `com.lucasluqui.launcher.mod`: Mod loader and file management (`ModManager`, `ZipMod`, `JarMod`, `Modpack`). Class mods mount into `code/config.jar`.
- `com.lucasluqui.launcher.editor`: Scene and loadout editors (`Silverweave`, `EditorsUI`).
- `com.lucasluqui.launcher.setting`: User preferences, JVM options, per-server connection settings (`SettingsManager`, `SettingsUI`).
- `com.lucasluqui.launcher.ui`: Swing UI panels based on `BaseUI`, `Scale` HiDPI support, and FlatLaf dark theme.
- `com.samskivert.util.HashIntMap`: Dual-interface compatibility bridge satisfying both modern samskivert (`IntMap`) and obfuscated `projectx-pcode.jar` Three Rings engine (`D`/`D$a`). It only matters for compiling and testing; the server process uses the game's own copy.
- Shortcuts (`LauncherApp.checkShortcut`): the Windows link, Linux `.desktop` file and macOS `~/Applications/Knight Launcher.app` are rebuilt whenever the launcher's Java path or install folder changes (`launcher.shortcutJava` holds a hash of both). When testing the launcher, run it with `-Duser.home=<scratch folder>` so your real shortcut is not overwritten.
- Training Hall movement uses the game's own controller (`VanillaCombatController`). It needs `Mobile._maxStep` to be non-zero or every step is clamped to nothing; `TrainingMovementTest` guards it. Names like `aeb()` that look equivalent can mean something else on another game build, so check fields, not accessors.
- Official vs private launches: a private (stock client) launch patches `code/config.jar` (`SettingsManager.applyConnectionSettings`) and records `launcher.configJarPrivate`; the next Official launch re-applies the Official values first. Connection settings are validated (port 1-65535, http(s) URLs) before a private launch.

## Design & Color Conventions
- All UI colors are defined in `com.lucasluqui.launcher.CustomColors`.
- Theme (same as the SKapsule app): neutral black surfaces (`#000000` titlebar to `#1E1E1E`/`#333333` components, see `CustomColors`) and one accent, `#AB4A81` (`CustomColors.ACCENT`, also FlatLaf's `@accentColor` in `Stylesheet`). Launch, Silverweave and the changelog button use it; status colors (update green, warning amber, danger red, Discord, Buy Me a Coffee yellow) and the mod-type badge colors stay. The app icons (`rsrc/img/icon-*.png`, `icon-512.icns`) are two colors only: `#AB4A81` ring and shield on black.
- Support & Donations: Buy Me a Coffee (`https://buymeacoffee.com/sirdankk`, brand yellow `#FFDD00`).
- Community Discord: `https://dankware.alwaysdata.net/discord`.
- Home screen layout: the five side buttons start at y=245 (35px, 4px apart) between the "Learn more" pill and the discord/bug/donate row at y=444; adding a button means re-spacing, not overlapping.
- Safeguard files and logic (`extractSafeguard`) are completely removed. URLs that are still upstream's (not rebranded): the CDN, the Flamingo server (`deploy.properties.template`) and the Java runtime downloads.

## Engine Background
- The game is built on the open-source Three Rings libraries (`threerings/narya`: Presents distributed objects, `threerings/clyde`: Tudey 2D/3D engine, `threerings/samskivert`); the server emulator speaks their protocol using the game's own (obfuscated) copies in `projectx-pcode.jar`.

## Known Gaps / Roadmap
- A real client logs in, walks Haven, enters the Training Hall, fights and logs off cleanly (verified). Movement felt stuttery at the old 100/200 ms update interval; the defaults are now 20 ms (see below). A Cocoa client cannot be started from the agent's shell (SIGTRAP in AppKit), so playtests are done by the user. Manual check after changes: host on loopback, **Connect & Play**, walk Haven, enter the Training Hall, fight a cube; then an Official launch after a private one.
- The server relies on obfuscated class and method names (`ClientSession`, `SceneManager`) and the client's receiver codes; a game update can break it. `SpiralServer.detectDataVersion` falls back to a fixed version string.
- Not implemented yet: mail attachments, shops, crafting, companions in the party HUD, loot and XP beyond crowns, the Missions/Board dungeon entry (`/mission` starts one), PvP. Protocol notes for these (from the client's bytecode, never captured live): shops need a server-owned catalog (the client ships none) and are opened by a listener-less `TudeySceneMarshaller` call; dungeon entry goes through the Missions panel and a `LevelPartyObject`; the game ships no dungeon layouts or enemy AI, so both are written here.
- Maven wrapper is the takari 0.5.6 one, which does not verify checksums; moving to the Apache wrapper would allow pinning.
- Planned: the Missions/Board entry to dungeons and loot/XP; deferred after that: PvP/arena, coin exchange, trade, rotating gates; guilds last. Also a shareable connection string.
- `SKapsule` / `SKapsule-iOS` mirror `ModManager.FILTER_LIST` by hand; keep them in step.
